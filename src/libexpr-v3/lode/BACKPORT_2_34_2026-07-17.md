The v3 branch carries **2658 commits** since the 2.34.0 merge-base, so a
history-replay was infeasible. Instead the port = (a) bring `src/libexpr-v3/`
wholesale from `c2b9803b2`, plus one satellite file, then (b) re-apply the
integration hooks — identified by grepping the core tree for v3 references —
adapted to 2.34's API. The v3-specific hunks were isolated by diffing
`13fe1c30f..c2b9803b2` (the clean pre-v3 2.35 point → v3 tip).

## Key finding: the v3 tree is API-stable across 2.34 ↔ 2.35

The big anticipated risk — "2.34 vs 2.35 differ in Value/EvalState/forceValue
signatures" — **did not materialize for the v3 library itself.** `libnixexprv3`
+ `v3-eval` compiled and linked against 2.34 headers with only harmless
`-Wunused-*` warnings. v3 touches TW only at FFI leaves (store, paths,
`realisePath`, `SourcePath`, derivation strict-merge, `flake::lockFlake`), and
those APIs are unchanged between 2.34.6 and 2.35.0. That is what makes this a
low-blast-radius port.

## The VM-v2 "phantom" deletions — no-ops on 2.34

The 2.35 pre-v3 base (`13fe1c30f`) still carried an **earlier, superseded**
in-`libexpr` bytecode evaluator ("VM v2"): `bytecode*.cc/.hh`, `ir*.cc/.hh`,
`vm.cc/.hh`, `nix-word.hh`, `bytecode-vm.cc` test, a direct `sqlite3` dep, the
`Expr::isBytecodeThunk`/`isBytecodeProxy` flags, and a block of `EvalState`
bytecode-cache members. A large share of the v3 branch's core-file diff is the
**removal** of VM-v2 (`eval.cc` −264, `eval.hh` −56, `nixexpr.hh`, the two
`meson.build` header/source lists). **None of VM-v2 exists on 2.34** (v3 dev
began on the 2.35 base), so every one of those removal hunks is a no-op here and
was correctly **skipped**. Likewise `value.hh`'s `isThunkOrApp` cast fix is moot:
that method is a 2.35 addition and is absent on 2.34 (and unused by v3).

## Integration-hook adaptation map (file : what : 2.34↔2.35 delta)

Load-bearing (required for v3-direct + a green brute):

1. **`meson.build`** — add `subproject('libexpr-v3')` after `libcmd`.
   *Clean* (anchor identical).
2. **`src/nix/meson.build`** — add `dependency('nix-expr-v3')`; add the darwin
   `-Wl,-stack_size,0x4000000` (64 MiB) link arg via a `nix_link_args` variable.
   *Clean.* Verified the linked `nix` carries `LC_MAIN stacksize 67108864`.
3. **`src/libutil/include/nix/util/eval-trace.hh`** — NEW file, brought wholesale
   from `c2b9803b2`. It exists on **neither** base (added by v3 work). Needed by
   `src/nix/eval.cc`'s `nix::evalTrace::mark` calls.
4. **`src/libutil/include/nix/util/meson.build`** — register `eval-trace.hh`.
   *Clean.*
5. **`src/nix/main.cc`** — 3 v3 includes (`v3/install.hh`, `v3/primop.hh`,
   `v3/heap_trace.hh`) + `v3::keepLibAlive()` link probe + `v3::setFlakeSettings(&flakeSettings)`
   + `v3::startHeapTrace()`. *Clean* — the 2.34 anchors (`savedArgv = argv`,
   `initGC()`, `flakeSettings.configureEvalSettings(evalSettings)`) are identical.
6. **`src/libcmd/installables.cc`** — the `NIX_V3_DIRECT_EVAL` mkThunk-only hook
   in `parseInstallables` (hand TW a thunk; do not pre-evaluate). *Clean* — the
   2.34 block is byte-identical to the 2.35 pre-v3 block; the APIs used
   (`state->baseEnv`, `parseExprFromFile`, `mkThunk(Env*, Expr*)`) all exist on 2.34.
7. **`src/nix/eval.cc`** — the `runV3DirectEval(...)` static function + the
   `CmdEval::run` dispatch hook (try v3-direct first under `NIX_V3_DIRECT_EVAL=1`,
   with `NIX_V3_REQUIRE=1` hard-fail-on-fallback).
   **← the one real API-shape delta.** 2.34's `src/nix/eval.cc` uses
   `using namespace nix;` at file scope; the 2.35 version wraps the file in
   `namespace nix { … }`. **Adaptation:** the static function was placed at file
   scope (after `using namespace nix;`) instead of inside a namespace block —
   semantically equivalent (`static` internal linkage either way; all `nix::`
   types are in scope via the using-directive). Every TW API the function
   references — `InstallableAttrPath`, `SourceExprCommand::{expr,file,getAutoArgs,
   getCommandBaseDir}`, `Installable::what()`, `lookupFileArg`,
   `SourcePath::{resolveSymlinks,readFile}` + `path.parent()`/`.abs()`,
   `EvalState::error<EvalError>().debugThrow()` — is present and
   signature-compatible on 2.34.
8. **`src/libutil/current-process.cc`** — wrap the `lvlError` "Failed to increase
   stack size" log in the existing `_NIX_TEST_NO_ENVIRONMENT_WARNINGS` gate.
   2.34 already gates the *sibling* `lvlWarn` "hard limit too low" log; the v3
   branch extended the same gate to the `lvlError` line. **Required for the gate:**
   `all-v3-tests.sh` exports `_NIX_TEST_NO_ENVIRONMENT_WARNINGS=1` and expects the
   darwin `setrlimit(RLIMIT_STACK)` EINVAL diagnostic suppressed so it can't leak
   into byte-id captures.

Diagnostic-only, **deliberately deferred** (not load-bearing; brute is 41/41
without them; each is a TW-vs-v3 trace-diffing aid, not v3 dispatch):

- `src/libexpr/include/nix/expr/eval-inline.hh` — the `NIX_TRACE_EVAL` tracing +
  `twValueTypeName` in TW's `forceValue`. Deferred to avoid touching 2.34's
  `forceValue` hot path (its iterative-loop shape differs from 2.35's).
  `eval-trace.hh` is still brought (needed by `nix/eval.cc`); only the TW-side
  emit is omitted.
- `src/libexpr/eval.cc` `TW_DBG_WITH_NAME`; `src/libexpr/primops.cc`
  `TW_DBG_IMPORT` / `TW_DBG_FROMJSON` — cold-path stderr diagnostics.

## Build-config lesson (Rule-0 verified, not speculated)

The first brute run was **40/41**, failing only `iterative-force` (`let-chain-5000`,
rc=137 = `timeout -SIGKILL` at 15 s — a timeout, not a crash: `curry-apply-5000`
and `app-spine-10000` passed). Root-caused by A/B measurement: the same expr took
~16–18 s on this port vs **8.59 s** on the canonical 2.35 `nix` binary on the
**same laptop**. Cause = `meson setup` defaulted to `buildtype=debug`
(`optimization=0`); the canonical build is `buildtype=debugoptimized`
(`optimization=2`). Reconfiguring `-Dbuildtype=debugoptimized` and rebuilding →
**41/41 ALL GREEN**. Not a port regression — the deep let-chain is pure v3-VM work
(brought wholesale, identical source) and is unaffected by any TW hook.
**Deployment note: build the CI/Hydra artifact at `-O2` (debugoptimized/release);
`-O0` roughly doubles v3 eval wall-time and trips the timing-sensitive suites.**

## Effort to full CI ship + remaining caveat

- **aarch64-darwin: DONE.** Builds, 41/41 brute, hello.drvPath byte-id.
- **x86_64-linux (the actual Hydra/linux-0 target): NOT validated this session.**
  This machine is darwin. The 2.35 v3 branch has a documented, *pre-existing*
  x86_64-linux port debt (stock `value.hh` `-Werror`, flake not packaging
  `nix-expr-v3`, libstdc++-vs-libc++ include debt — see the project memory's
  x86_64 entry). The backport inherits exactly that debt, no more: the 2.34-v3
  branch's *hook* deltas are API-clean, so the linux gap is the same v3
  linux-bring-up already tracked upstream, not new work introduced here.
  Estimate to green the linux CI artifact: bounded by that existing v3 linux
  bring-up, not by the 2.34 rebase (≈ the same 1–3 day surface already scoped on
  the 2.35 branch). `nix-eval-jobs@2.34.1` / patched Hydra rebuild against the
  v3-carrying `libnixexpr` with no version bump, as intended.
